# Spec: 미니 방명록 (guestbook-202204175)

Status: ready-for-agent

## Problem Statement

방문자가 회원가입이나 로그인 없이 짧은 글을 남기고, 다른 사람들이 남긴 글을 한눈에 볼 수 있는 공간이 필요하다. 계정이 없으니 "이 글을 쓴 사람만 고치거나 지울 수 있다"는 것을 증명할 다른 방법이 있어야 한다. 누구든 남의 글을 고치거나 지울 수 있으면 방명록을 믿을 수 없게 된다. 또 과제 제출물이므로 누가 만들었는지(개발자 이름과 학번)가 화면에 드러나야 한다.

## Solution

한 페이지짜리 방명록을 만든다. 누구나 Author name, Message, Entry password를 입력해 Entry를 남길 수 있다. 모든 Entry는 Written at 기준 최신순으로 목록에 쌓인다. 각 Entry에는 [수정]/[삭제] 버튼이 있다. 작성할 때 정한 Entry password를 맞게 입력한 사람만 그 Entry의 Message를 고치거나 Entry를 지울 수 있다. 비밀번호가 틀리면 요청이 거부되고, 그 Entry의 폼 안에 "비밀번호가 일치하지 않습니다"라는 안내가 뜬다. 페이지 상단에는 제목 "방명록"과 `개발자: 권태현 (202204175)`가 표시된다.

## User Stories

### 작성

1. 방문자로서, 이름·메시지·비밀번호만 입력해 Entry를 남기고 싶다. 가입 없이 바로 흔적을 남기기 위해서다.
2. 방문자로서, 작성 폼이 페이지 상단 목록 바로 위에 있기를 원한다. 찾지 않고 바로 쓰기 위해서다.
3. 방문자로서, Entry를 남기면 폼이 비워지고 내 Entry가 목록 맨 위에 바로 보이길 원한다. 제대로 등록됐는지 확인하기 위해서다.
4. 방문자로서, 이름·메시지·비밀번호 중 하나라도 비었거나 공백뿐이면 등록이 거부되고 어떤 칸이 문제인지 알고 싶다. 고쳐서 다시 제출하기 위해서다.
5. 방문자로서, Author name이 1–20자여야 한다는 것을 알고 싶다. 너무 긴 이름으로 제출했다가 거부당하지 않기 위해서다.
6. 방문자로서, Message가 1–500자여야 한다는 것을 알고 싶다. 길이 제한 안에서 글을 쓰기 위해서다.
7. 방문자로서, Entry password가 4–32자여야 한다는 것을 알고 싶다. 조건에 맞는 비밀번호를 정하기 위해서다.
8. 방문자로서, 이름이나 메시지 앞뒤에 실수로 넣은 공백이 저장되지 않기를 원한다. 목록이 깔끔하게 보이기 위해서다.
9. 방문자로서, 검증에 실패했을 때 입력한 내용이 지워지지 않기를 원한다. 처음부터 다시 쓰지 않기 위해서다.
10. 방문자로서, 비밀번호 입력칸이 가려진 채로(마스킹) 입력되길 원한다. 옆 사람이 보지 못하게 하기 위해서다.
11. 방문자로서, 여러 줄로 쓴 메시지의 줄바꿈이 그대로 유지되길 원한다. 쓴 모양대로 읽히게 하기 위해서다.
12. 방문자로서, 다른 사람과 같은 이름을 써도 Entry를 남길 수 있기를 원한다. Author name은 표시용일 뿐이기 때문이다.

### 조회

13. 방문자로서, 페이지에 들어오면 전체 Entry 목록을 볼 수 있기를 원한다. 다른 사람들이 남긴 글을 읽기 위해서다.
14. 방문자로서, 목록이 가장 최근에 작성된 Entry부터 보이길 원한다. 새 글을 먼저 보기 위해서다.
15. 방문자로서, 각 Entry의 Author name, Message, Written at을 함께 보고 싶다. 누가 언제 무슨 말을 남겼는지 알기 위해서다.
16. 방문자로서, Written at이 한국 시각(`YYYY-MM-DD HH:mm`)으로 보이길 원한다. 서버가 어디서 돌든 헷갈리지 않기 위해서다.
17. 방문자로서, 수정된 적 있는 Entry에 "(수정됨)" 표시가 보이길 원한다. 처음 쓴 그대로인지 알기 위해서다.
18. 방문자로서, 누가 Message에 HTML이나 스크립트를 써 넣어도 일반 텍스트로만 보이길 원한다. 페이지가 깨지거나 악성 코드가 실행되지 않게 하기 위해서다.
19. 방문자로서, 아직 Entry가 하나도 없으면 "아직 작성된 글이 없습니다" 안내를 보고 싶다. 페이지가 고장 난 게 아님을 알기 위해서다.
20. 방문자로서, 다른 사람이 새 Entry를 남긴 뒤 페이지를 새로고침하면 그 Entry가 보이길 원한다. 항상 최신 목록을 보기 위해서다.

### 수정

21. 글쓴이로서, 내 Entry의 [수정] 버튼을 누르면 그 Entry 안에 수정 폼이 펼쳐지길 원한다. 어느 글을 고치는지 헷갈리지 않기 위해서다.
22. 글쓴이로서, 수정 폼에 기존 Message가 미리 채워져 있기를 원한다. 일부분만 고치기 위해서다.
23. 글쓴이로서, 새 Message와 Entry password를 입력해 Message를 고치고 싶다. 오타나 내용을 바로잡기 위해서다.
24. 글쓴이로서, 비밀번호가 맞으면 수정 폼이 닫히고 바뀐 Message와 "(수정됨)" 표시가 보이길 원한다. 수정이 반영됐는지 확인하기 위해서다.
25. 글쓴이로서, 수정해도 내 Entry의 목록 위치(Written at)가 바뀌지 않길 원한다. 목록 순서가 작성 순서를 그대로 나타내기 위해서다.
26. 글쓴이로서, Author name과 Entry password는 수정 대상이 아니라는 것을 알고 싶다. 수정 폼에서는 Message만 바꿀 수 있다.
27. 방문자로서, 비밀번호를 틀리면 수정이 거부되고 그 Entry의 폼 안에 "비밀번호가 일치하지 않습니다"가 보이길 원한다. 왜 반영되지 않았는지 알기 위해서다.
28. 글쓴이로서, 비밀번호를 틀렸을 때 고쳐 쓴 Message가 폼에 그대로 남아 있기를 원한다. 비밀번호만 다시 입력하기 위해서다.
29. 글쓴이로서, 새 Message도 1–500자 규칙을 지켜야 하고 어기면 안내를 받고 싶다. 빈 글로 바꿔 버리지 않기 위해서다.
30. 글쓴이로서, 수정 폼의 [취소]를 누르면 아무것도 바뀌지 않고 폼이 닫히길 원한다. 마음이 바뀌었을 때 되돌리기 위해서다.
31. 방문자로서, 남의 Entry라도 [수정] 버튼은 보이지만 비밀번호 없이는 아무것도 바꿀 수 없기를 원한다. 권한은 비밀번호로만 결정된다.

### 삭제

32. 글쓴이로서, 내 Entry의 [삭제] 버튼을 누르면 그 Entry 안에 비밀번호 입력 폼이 펼쳐지길 원한다. 실수로 바로 지워지지 않게 하기 위해서다.
33. 글쓴이로서, 비밀번호가 맞으면 Entry가 목록에서 즉시 사라지길 원한다. 삭제됐는지 확인하기 위해서다.
34. 방문자로서, 비밀번호를 틀리면 삭제가 거부되고 그 Entry의 폼 안에 "비밀번호가 일치하지 않습니다"가 보이길 원한다. 왜 지워지지 않았는지 알기 위해서다.
35. 글쓴이로서, 삭제 폼의 [취소]를 누르면 폼이 닫히고 Entry가 그대로 남길 원한다.
36. 글쓴이로서, 삭제한 Entry는 완전히 없어지길 원한다. 흔적이 남지 않게 하기 위해서다.

### 경합과 오류

37. 방문자로서, 페이지를 연 사이 다른 사람이 이미 지운 Entry를 수정하거나 삭제하려 하면 "이미 삭제된 글입니다" 안내를 보고, 목록이 최신으로 갱신되길 원한다. 없는 글과 씨름하지 않기 위해서다.
38. 방문자로서, 제출 중에는 버튼이 비활성화되거나 진행 중 표시가 보이길 원한다. 두 번 눌러 중복 등록되지 않게 하기 위해서다.
39. 방문자로서, DB 연결 실패처럼 예상치 못한 오류가 나면 "잠시 후 다시 시도해 주세요" 같은 일반 안내를 보고 싶다. 내부 오류 메시지가 노출되지 않게 하기 위해서다.
40. 방문자로서, 비밀번호가 틀린 경우와 글이 없는 경우의 안내가 서로 구분되길 원한다. 무엇이 문제인지 정확히 알기 위해서다.

### 보안

41. 글쓴이로서, 내 Entry password가 DB에 평문으로 저장되지 않길 원한다. DB가 유출돼도 비밀번호가 드러나지 않게 하기 위해서다.
42. 글쓴이로서, 목록 화면이나 페이지 데이터 어디에도 내 Entry password(해시 포함)가 노출되지 않길 원한다.
43. 글쓴이로서, 여러 곳에서 같은 비밀번호를 써도 저장된 해시가 서로 달라 보이길 원한다(글마다 다른 salt).

### 개발자 표시와 제출

44. 채점자로서, 페이지 상단에서 `개발자: 권태현 (202204175)`를 볼 수 있기를 원한다. 누구의 제출물인지 확인하기 위해서다.
45. 채점자로서, Vercel 배포 URL에 접속해 작성·조회·수정·삭제가 실제로 동작하는 것을 확인하고 싶다.
46. 채점자로서, GitHub 저장소, Vercel 프로젝트, Neon 프로젝트 이름이 모두 `guestbook-202204175`이기를 원한다.
47. 휴대폰 사용자로서, 좁은 화면에서도 폼과 목록이 가로 스크롤 없이 읽히길 원한다.

## Implementation Decisions

### 모듈 구성

- **Guestbook 모듈 (깊은 모듈, 유일한 테스트 seam)**: 방명록의 모든 규칙을 담는다. 다음 네 가지 동작을 제공한다.
  - `listEntries()`: 모든 Entry를 Written at 내림차순으로 반환한다. 반환값에는 id, Author name, Message, Written at, Edited 여부만 들어가고 비밀번호 정보는 절대 포함하지 않는다.
  - `writeEntry({ authorName, message, password })`
  - `editMessage({ id, message, password })`
  - `deleteEntry({ id, password })`
  - 쓰기 동작은 예외를 던지지 않고 결과 값을 돌려준다. 결과는 `{ ok: true }` 또는 `{ ok: false, reason }` 중 하나이고, reason은 다음 셋 중 하나다.
    - `invalid`: 필드별 오류 메시지를 함께 준다.
    - `wrong-password`
    - `not-found`
  - 검증(trim, 길이 제한), 비밀번호 해시와 비교, "Message만 수정 가능" 규칙이 모두 이 모듈 안에 있다.
  - 저장소는 생성 시 주입받는다. 프로덕션에서는 Neon 저장소를, 테스트에서는 인메모리 저장소를 쓴다.
- **Entry 저장소 (어댑터)**: Guestbook 모듈이 필요로 하는 최소한의 영속화 인터페이스다. 전체 조회, 삽입, id로 조회(해시 포함), Message 갱신, 삭제를 제공한다.
  - Neon 구현은 `@neondatabase/serverless`로 SQL을 직접 작성한다. ORM은 쓰지 않는다.
  - 인메모리 구현은 테스트용이다.
- **Server Actions (얇은 어댑터)**: 작성, 수정, 삭제 각각 하나씩 둔다. 하는 일은 FormData를 읽고, Guestbook 모듈을 호출하고, 성공하면 `revalidatePath`로 목록을 갱신하는 것뿐이다. 결과는 폼 상태로 돌려준다. 규칙은 넣지 않는다.
- **UI**:
  - 서버 컴포넌트인 페이지가 `listEntries()`로 목록을 렌더링한다. 매 요청 최신 데이터를 보여야 하므로 정적 캐시하지 않는다.
  - 작성 폼, 그리고 Entry별 수정 폼과 삭제 폼은 클라이언트 컴포넌트다. React의 폼 액션 상태 훅으로 결과(오류 문구, 필드별 오류)를 표시한다.
  - Next.js 16의 정확한 API(Server Actions, revalidate, 폼 상태 훅)는 구현 전에 `node_modules/next/dist/docs/`를 확인한다.

### 스키마

단일 테이블 `entries`를 둔다. 스키마는 저장소에 SQL 파일로 두고 Neon에 한 번 적용한다.

| 컬럼 | 타입 | 비고 |
|---|---|---|
| id | uuid 또는 bigint identity | PK |
| author_name | text | NOT NULL |
| message | text | NOT NULL |
| password_hash | text | NOT NULL, `salt:hash` 형태 |
| created_at | timestamptz | NOT NULL, 기본값 now(). Written at |
| updated_at | timestamptz | NULL 허용. NULL이 아니면 Edited |

- `created_at DESC` 정렬로 목록을 조회한다.

### 비밀번호

- `node:crypto`의 scrypt와 Entry마다 무작위로 만든 salt로 해시한다. 비교는 `timingSafeEqual`로 한다. 추가 의존성은 없다.
- 비밀번호는 trim하지 않는다. 입력한 그대로 해시한다.

### 검증 규칙 (서버 기준)

| 필드 | trim | 허용 길이 |
|---|---|---|
| Author name | 앞뒤 공백 제거 | 1–20자 |
| Message | 앞뒤 공백 제거 | 1–500자 |
| Entry password | 하지 않음 | 4–32자 |

- 클라이언트에도 `maxLength`/`required`를 걸지만, 판단 기준은 서버 검증이다.
- 글자 수는 코드 포인트가 아니라 JavaScript 문자열 길이 기준으로 세도 무방하다. 과제 범위에서 이 차이는 수용한다.

### 표시

- Written at은 `Asia/Seoul` 시간대로 `YYYY-MM-DD HH:mm` 형식으로 명시적으로 포맷한다. Vercel 서버는 UTC로 동작하므로 기본 로케일 포맷에 의존하지 않는다.
- Message는 React의 기본 이스케이프로 일반 텍스트로 렌더링하고, 줄바꿈은 `white-space: pre-wrap`으로 유지한다. HTML을 직접 주입하는 방식은 금지한다.
- 오류 문구:

| 상황 | 문구 |
|---|---|
| 비밀번호 불일치 | "비밀번호가 일치하지 않습니다" |
| Entry 없음 | "이미 삭제된 글입니다" |
| 예상치 못한 오류 | "잠시 후 다시 시도해 주세요" |

### 설정

- `DATABASE_URL` 환경변수 하나로 Neon에 접속한다. 로컬에서는 `.env.local`, Vercel에서는 프로젝트 환경변수로 설정한다.
- `package.json`의 name을 `guestbook-202204175`로 바꾼다.
- 개발자 이름과 학번은 상수 한 곳에 둔다.

## Testing Decisions

- **좋은 테스트의 기준**: 외부에서 관찰 가능한 동작만 검증한다. Guestbook 모듈의 공개 동작 네 가지(목록, 작성, 수정, 삭제)를 호출하고, 결과 값과 이후 `listEntries()`에 보이는 내용만 확인한다. 해시 형식이나 저장소 내부 호출 순서 같은 구현 세부는 검증하지 않는다.
- **테스트 seam은 Guestbook 모듈 하나**다. 인메모리 Entry 저장소를 주입해 DB 없이 빠르게 돈다. Server Actions와 UI는 얇은 어댑터라 단위 테스트하지 않는다.
- **도구**: Vitest를 새로 추가하고 `npm test` 스크립트를 둔다.
- **다룰 시나리오**:
  - 작성 성공 후 목록 맨 위에 나타남
  - 여러 개를 쓰면 최신순으로 정렬됨
  - 필드별 검증 실패: 빈 값, 공백뿐인 값, 길이 경계(20/21자, 500/501자, 3/4/32/33자)
  - trim 동작
  - 올바른 비밀번호로 수정하면 Message가 바뀌고 Edited가 되며 순서는 그대로임
  - 틀린 비밀번호로 수정하면 `wrong-password`가 오고 아무것도 바뀌지 않음
  - 없는 id로 수정·삭제하면 `not-found`가 옴
  - 올바른 비밀번호로 삭제하면 목록에서 사라짐
  - 틀린 비밀번호로 삭제하면 `wrong-password`가 오고 Entry가 남음
  - `listEntries()` 결과에 비밀번호 정보가 없음
  - 같은 비밀번호로 쓴 두 Entry가 서로 독립적임
- **기존 선례**: 저장소에 아직 테스트가 없다. 이 스펙이 첫 선례가 된다.
- **수동 확인**: 실제 Neon 연동과 UI 흐름은 로컬 `next dev`와 Vercel 배포 URL에서 작성·조회·수정·삭제, 비밀번호 불일치 안내까지 직접 확인한다.

## Out of Scope

- 회원가입, 로그인, 세션, 관리자 계정이나 관리자용 삭제 권한
- 비밀번호 분실 시 복구 또는 변경
- Author name 수정
- 비밀번호 시도 횟수 제한(rate limit), CAPTCHA, 스팸 필터
- 소프트 삭제, 수정 이력 보관
- 페이지네이션, 검색, 정렬 옵션
- 실시간 갱신(WebSocket, 폴링). 최신 목록은 새로고침이나 작업 후 revalidate로 반영한다.
- 마크다운이나 HTML 서식, 이미지 첨부, 이모지 반응, 댓글
- 다국어 지원(UI는 한국어만)
- 실제 Neon DB에 붙는 자동화 통합 테스트와 E2E 테스트
